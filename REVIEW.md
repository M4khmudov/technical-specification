# Ревью: инструмент ассистента `reserve_material`

```python
@assistant_tool("reserve_material")
async def reserve_material(args: dict, db) -> str:
    """ Зарезервировать материал под задание."""
    logger.info("tool call: %s", args)
    batches = await db.fetch_all(
        f"SELECT * FROM batches WHERE material_code = '{args['material']}' "
        "ORDER BY id DESC"
    )
    need = float(args["qty"])
    for b in batches:
        take = min(b["qty"] - b["reserved"], need)
        await db.execute(
            "UPDATE batches SET reserved = reserved + :t WHERE id = :id",
            {"t": take, "id": b["id"]},
        )
        need -= take
        if need == 0:
            break
    return f" Готово , зарезервировано  {args['qty']}"
```

**Итог: в таком виде вливать нельзя.** Функция открывает SQL-инъекцию любому, кто может
повлиять на текст разговора с моделью, меняет склад без подтверждения и прав, теряет резервы
при параллельных запросах, резервирует не те партии и не в том порядке и сообщает «Готово»,
даже когда ничего не зарезервировано. Ниже — проблемы по убыванию важности и как исправить.

Важность: 🔴 критично (уязвимость или порча данных) · 🟠 серьёзно (неверная работа) ·
🟡 стоит исправить.

---

## 🔴 Критично

### 1. SQL-инъекция через аргумент от модели

`args['material']` подставляется в SQL f-строкой. Аргументы инструмента приходят **от модели**,
а модель повторяет то, что прочитала: вопрос пользователя, комментарий к партии, загруженный
файл. Строка вида `x' OR '1'='1` резервирует всё подряд, а с драйвером, допускающим несколько
выражений, — `x'; UPDATE batches SET reserved = 0; --`. Это промпт-инъекция, превращённая в
SQL-инъекцию: атакующему даже не нужен доступ к API, достаточно оставить текст в данных.

**Исправить:** только параметры запроса или ORM (`select(Batch).where(Batch.material_id == …)`);
материал искать по коду через справочник и отвечать «не найден», а не строить SQL из текста.

### 2. Данные меняются без подтверждения пользователя

Инструмент сразу пишет в `batches`. По требованиям ассистент меняет данные только после кнопки
«Подтвердить», а до этого показывает, что собирается сделать. Сейчас модель может
зарезервировать материал по собственной инициативе, по ошибочно понятой фразе или по команде,
спрятанной в данных.

**Исправить:** инструмент действия только **готовит предложение** (что именно и сколько
зарезервирует, ожидаемый дефицит) и сохраняет его; выполняет его эндпоинт подтверждения по
нажатию кнопки — тем же кодом, что и обычная кнопка интерфейса.

### 3. Нет прав и нет пользователя; логика в обход сервисного слоя

Функция получает сырое соединение `db` и не знает, **кто** просит. Кладовщик (или кто угодно,
у кого есть чат) резервирует материалы, хотя кнопкой этого сделать не может. При этом
резервирование здесь написано заново, а не вызывает тот же сервис, что кнопка, — правила
неизбежно разойдутся (что уже и видно: FIFO, статусы, связь с заданием).

**Исправить:** инструмент получает контекст с текущим пользователем и вызывает функцию
сервисного слоя, которая первой строкой проверяет право (`require(user, JOB_MANAGE)`), — ту же,
что вызывает кнопка. «Через ассистента нельзя сделать то, что нельзя сделать кнопкой» тогда
выполняется по построению.

### 4. Гонка: два одновременных запроса резервируют один и тот же остаток

Свободный остаток читается одним запросом, а резерв пишется другими, без транзакции и
блокировок. Два параллельных вызова оба видят «свободно 10», оба берут по 8 и оба делают
`reserved = reserved + 8` — зарезервировано 16 из 10. Требование «два одновременных запроса не
могут зарезервировать один и тот же остаток» нарушено.

**Исправить:** одна транзакция; партии блокировать `SELECT … FOR UPDATE` в едином порядке
(материал → дата поступления → id), чтобы исключить взаимоблокировки; после ожидания
блокировки перечитывать свободный остаток. Последний рубеж — `CHECK (reserved_qty <= remaining_qty)`
в БД. Обязательно тест с параллельными запросами — без блокировки он показывает перерасход.

### 5. LIFO вместо FIFO

`ORDER BY id DESC` берёт **новые** партии первыми. По требованиям — FIFO: сначала самые старые.
К тому же `id` — не дата поступления: партия, оформленная задним числом, получит большой id.

**Исправить:** `ORDER BY received_on, id` (по возрастанию).

### 6. Резервируются непринятые партии

Нет фильтра по статусу: в резерв попадают партии «На проверке» и «Брак», хотя использовать
можно только принятые.

**Исправить:** `WHERE status = 'accepted'` (и только партии со свободным остатком).

## 🟠 Серьёзно

### 7. Резерв не привязан к заданию

Docstring говорит «под задание», но задания в аргументах нет, а резерв — просто число в партии.
Потом невозможно понять, чей это резерв, снять его при отмене задания, списать при
завершении, показать «светофор» и историю партии.

**Исправить:** таблица резервов `(job_id, batch_id, quantity)` + движение в истории партии;
`batches.reserved_qty` меняется вместе с ней в одной транзакции. Резервировать не «материал
вообще», а потребность конкретного задания по рецепту.

### 8. `float` для количеств

`float(args["qty"])` и арифметика на float: `0.3 - 0.1 - 0.2` даёт `5.55e-17`, а не 0. Условие
`need == 0` может не сработать никогда — цикл продолжит резервировать «хвосты» в следующих
партиях. Деньги и количества — только `Decimal` в коде и `numeric` в БД.

**Исправить:** `Decimal`, сравнение `need <= 0`, количества как `numeric(14,3)`.

### 9. Нехватка не обрабатывается, а ответ врёт

Если остатка мало, цикл заканчивается с `need > 0`, а функция возвращает «Готово,
зарезервировано {qty}» — **запрошенное** количество, а не фактическое. Модель передаст
пользователю неверное число, задание будет считаться обеспеченным. По требованиям при
нехватке — частичный резерв и **дефицит**, а запустить задание с дефицитом нельзя. Тот же
«Готово» вернётся, если материал не найден вовсе (пустой список партий).

**Исправить:** возвращать структурированный результат: сколько зарезервировано по каким
партиям и сколько не хватило; «материал не найден» — отдельной понятной ошибкой.

### 10. Аргументы не валидируются

`args: dict` без схемы: нет ключа — `KeyError` и 500; `qty = -5` даёт отрицательный `take` и
**уменьшает** чужие резервы; `"nan"`, `"inf"`, `"1e9"` проходят через `float`. Аргументы модели —
внешний ввод.

**Исправить:** Pydantic-схема (`material: str` с длиной, `quantity: Decimal > 0` с
ограничением разрядов, `job_id: int`), её же JSON Schema — модели в описании инструмента;
ошибка валидации возвращается модели текстом, а не роняет ход.

### 11. Используется `qty`, а не текущий остаток; `take` может быть ≤ 0

`b["qty"] - b["reserved"]` — это пришедшее количество минус резерв; списанное в производство не
учитывается, поэтому резервируется уже израсходованный материал. Для партий без свободного
остатка `take = 0` (лишний UPDATE), а если данные уже испорчены (`reserved > qty`) — `take < 0`
и резерв уменьшается.

**Исправить:** свободно = `remaining_qty - reserved_qty`; пропускать партии с `free <= 0`;
выбирать сразу только партии со свободным остатком.

### 12. Нет транзакции: частичная запись при ошибке

Каждый `UPDATE` выполняется сам по себе. Ошибка на третьей партии оставит резерв по двум
первым, и повторный вызов зарезервирует их снова.

**Исправить:** всё резервирование — одна транзакция (с блокировками из п. 4), commit в конце.

### 13. Нет журнала изменений

Не записано, кто, когда и что зарезервировал, что было и что стало. Требование к журналу и
история партии («резерв под задание №…») не выполняются.

**Исправить:** запись в журнал (ФИО, время, до/после) и движение «резерв» по каждой партии.

## 🟡 Стоит исправить

### 14. Сырые аргументы модели в логе

`logger.info("tool call: %s", args)` пишет в лог всё, что прислала модель, — включая имена,
которые туда попали, и текст инъекций. По требованиям в логах персональных данных нет.

**Исправить:** логировать имя инструмента, длительность и исход, без значений аргументов.

### 15. Текст ответа

`" Готово , зарезервировано  {qty}"` — лишние пробелы, нет единиц, число в «машинном» виде
(`2.5` вместо `2,5 кг`). Модели лучше отдавать структуру (JSON), а человекочитаемую сводку
формировать отдельно — тогда и модель не перескажет неверный текст.

### 16. Лишняя работа

`SELECT *` всех партий материала, даже если нужна одна; по `UPDATE` на каждую партию в цикле.
При сотнях партий — лишние запросы и долгие блокировки.

**Исправить:** выбирать только нужные колонки и только принятые партии со свободным
остатком, в порядке FIFO, и остановиться, как только потребность закрыта.

### 17. Описание для модели

Docstring с пробелом в начале — единственное, что видит модель. Нет описания аргументов,
единиц измерения, того, что действие требует подтверждения. Модель будет угадывать формат
`qty` (кг или граммы?) и вызывать инструмент там, где не нужно.

### 18. Нет тестов

Нужны минимум: FIFO, частичный резерв и дефицит, только принятые партии, два параллельных
резерва, отказ по правам через ассистента, невалидные аргументы, «данные не меняются до
подтверждения».

## Как бы я переписал

Инструмент — тонкая обёртка: проверяет аргументы схемой и **готовит** предложение; данные
меняет кнопка «Подтвердить» тем же сервисом, что и интерфейс.

```python
class ReserveArgs(BaseModel):
    job_number: int = Field(gt=0, description="Номер задания, под которое резервируем")


async def reserve_for_job(ctx: ToolContext, args: ReserveArgs) -> ToolOutcome:
    """Дозарезервировать материалы под задание. НЕ выполняет действие: готовит его,
    пользователь подтверждает кнопкой."""
    action = await actions.propose_reserve(ctx.session, ctx.user, args.job_number)  # права — внутри
    return ToolOutcome(
        {"status": "awaiting_user_confirmation", "preview": action.preview},
        action.preview["title"],
        extra={"action": action_card(action)},
    )
```

Сервис, который вызывают и кнопка, и подтверждение:

```python
async def reserve_job(session, actor, job_id) -> JobOut:
    require(actor, Permission.JOB_MANAGE)                     # права — как у кнопки
    job = await _lock_job(session, job_id)                    # SELECT … FOR UPDATE
    _require_status(job, (JobStatus.PLANNED,), "дозарезервировать")
    need = _deficits(job)                                     # Decimal, по рецепту задания
    batches = await session.scalars(
        select(Batch)
        .where(
            Batch.material_id.in_(need),
            Batch.status == BatchStatus.ACCEPTED,             # только принятые
            Batch.remaining_qty > Batch.reserved_qty,         # только со свободным остатком
        )
        .order_by(Batch.material_id, Batch.received_on, Batch.id)  # FIFO и единый порядок блокировок
        .with_for_update()
        .execution_options(populate_existing=True)            # свежие значения после ожидания
    )
    for batch in batches:
        take = min(batch.remaining_qty - batch.reserved_qty, need[batch.material_id])
        if take <= 0:
            continue
        batch.reserved_qty += take                            # CHECK reserved <= remaining в БД
        job.reservations.append(Reservation(batch=batch, quantity=take, ...))
        session.add(BatchMovement(kind=MovementKind.RESERVE, quantity=take, ...))
        need[batch.material_id] -= take
    audit.record(session, actor, "job", job.id, "reserve", before=..., after=...)
    await session.commit()                                    # всё одной транзакцией
    return await get_job(session, job_id)                     # с остаточным дефицитом и «светофором»
```

В проекте это реализовано так: резервирование — `backend/app/services/production.py`
(`_lock_batches`, `_reserve_deficits`, `plan_job`, `reserve_job`), действие с подтверждением —
`backend/app/services/actions.py` и инструмент `create_job` в
`backend/app/assistant/tool_set.py`, тесты — `tests/test_production.py` (FIFO, частичный
резерв, параллельные резервы), `tests/test_tools.py` и `tests/test_safety.py` (права,
подтверждение, инъекции).
