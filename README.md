# Свечная мастерская: учёт производства и ИИ-ассистент

Учёт склада и производства мастерской ароматических свечей: сырьё приходит партиями,
резервируется по FIFO и расходуется на производственные задания. Поверх — ИИ-ассистент: он
отвечает на вопросы по данным, строит графики в Code Interpreter и готовит задания, которые
пользователь подтверждает кнопкой.

- Ревью кода из части 3 — [REVIEW.md](REVIEW.md)
- Изменения по разбору от 14.10 (B1…M13, со ссылками на коммиты) — [CHANGES.md](CHANGES.md)
- Отчёты эталонных вопросов — [`backend/evals/reports/`](backend/evals/reports/)

## Запуск

```bash
cp .env.example .env      # вписать OPENAI_API_KEY; без ключа работает всё, кроме ассистента
docker compose up -d --build
```

Поднимаются PostgreSQL, Redis, бэкенд, воркер, моки внешних сервисов и фронтенд;
применяются миграции и создаются демо-данные (повторный запуск ничего не дублирует,
`SEED_DEMO_DATA=false` — пустая база). Воркер и фронтенд стартуют, когда бэкенд здоров.

### Сценарий для проверки

1. `tech` → «Ассистент» → «Чего не хватит на задания ближайшей недели?» — дефицит кокосового
   воска у задания «Ваниль» на пятницу.
2. «Запланируй 200 свечей «Лаванда» на пятницу» → карточка с предпросмотром → «Подтвердить» →
   ссылка на задание. В карточке задания — резерв по FIFO и «светофор».
3. «Построй график расхода воска по неделям за квартал» — график в чате, код под ответом.
4. «Сколько стоит соевый воск?» — средняя себестоимость и цены последних поступлений.
5. «Отмени задание №27» — ассистент честно говорит, что отмена — кнопка в карточке задания.

## Модели и почему

| | Модель | Зачем |
| --- | --- | --- |
| Основная | `openai:gpt-4.1` | надёжный вызов инструментов, Code Interpreter в Responses API |
| Запасная | `openai:gpt-4.1-mini` | тот же провайдер: файлы Code Interpreter и формат инструментов подходят без изменений; отдельные лимиты — помогает при 429 |
| Судья эталонов | `openai:gpt-5.4` | другая, более сильная модель: оценивать ответы той же моделью — снисходительно; gpt-5.4-mini ставил 1 дословно верным ответам |

Модели задаются строкой «провайдер:модель» (`LLM_PRIMARY`, `LLM_FALLBACK`, `EVAL_JUDGE_MODEL`).
При 429, 5xx, 408, таймауте и сбое внутри потока ассистент переходит на запасную; прочие 4xx —
ошибка запроса, не повторяется. Свой тонкий LLM-слой без фреймворков: Responses API нужен ради
встроенного Code Interpreter, а один протокол провайдера и роутер проще проверить тестами.

## Решения и допущения

**Решения**

- **Права — в сервисном слое**, первой строкой изменяющей операции. Кнопка и инструмент
  ассистента вызывают одну функцию: через ассистента нельзя больше, чем кнопкой.
- **Действие ассистента — предложение.** `create_job` ничего не меняет: сохраняет предложение с
  предпросмотром. Выполняет его «Подтвердить» тем же сервисом, что кнопка интерфейса.
  Предложение сначала «занимается» под блокировкой строки, поэтому два одновременных
  «Подтвердить» создают одно задание. Других действий у ассистента нет.
- **Конкурентность резервов:** блокировка строки задания, затем партий `SELECT … FOR UPDATE` в
  едином порядке (материал → дата → id) с перечитыванием после ожидания; CHECK
  `0 ≤ резерв ≤ остаток` в БД.
- **Маркировка — transactional outbox:** отчёт создаётся в одной транзакции с завершением,
  завершение не ждёт ни сервис, ни Redis (постановка в очередь — не дольше 1 с). Воркер arq
  отправляет с растущей паузой (5 с … 5 мин, джиттер), ключ идемпотентности один на все
  попытки, каждая попытка — в журнале. После 8 неудач — «Не отправлен», руководитель
  повторяет вручную (новый круг попыток).
- **Время мастерской — Москва** (`TIMEZONE`): «сегодня», «на этой неделе», «в пятницу» не
  зависят от UTC сервера и часового пояса браузера.
- **Персональные данные:** ФИО и поставщики заменяются псевдонимами `Сотрудник-N` /
  `Поставщик-N` (N — id) до отправки в модель, обратно — только перед показом. Файлы для Code
  Interpreter: CSV — текстом с псевдонимами, XLSX — новая книга только из значений ячеек
  (без свойств документа, комментариев, колонтитулов). В журналах доступа — путь без
  параметров запроса.
- **Защита от инъекций — устройством системы:** нет разрушающих инструментов; память
  запоминает только дословно сказанное пользователем (цитата сверяется с его сообщением и не
  должна быть текстом из данных) и никогда — правила, подтверждения, права; под ответом с
  обещанием действия без предложения и с числами без обращения к данным — предупреждение.
- **Генерация ответа — в фоновой задаче**, SSE только читает её события: «Остановить», обрыв
  связи и сбой модели сохраняют показанный текст с пометкой.

**Допущения**

- Статусы задания: Черновик → Запланировано → В работе → Завершено → Сервис маркировки.
  Отмена — только из первых двух. Черновик ничего не резервирует; его «светофор» показывает,
  хватит ли свободного остатка, себестоимость — оценка по средним ценам склада.
- Матрица ролей в ТЗ не задана — распределено по смыслу ролей (таблица выше).
- Курс — только рабочие дни (как ЦБ); в выходные и праздники берётся последний предыдущий.
- Дата поступления не в будущем; задание нельзя создать или запланировать на прошедшую дату.
- При завершении пустой факт по материалу = норма; штучные материалы — только целым числом.
- **Перерасход при завершении досписывается только из свободного остатка.** Если нужный
  материал физически лежит на складе, но зарезервирован под другие задания, завершить задание
  нельзя: система не отнимает материал у чужого задания молча. Последствие для технолога —
  сначала освободить материал (отменить или перенести другое задание, оформить поступление),
  затем завершить. Альтернатива — забирать из чужого резерва и переводить то задание в
  дефицит — честнее отражает склад, но меняет чужие задания без ведома их владельца; не
  сделано сознательно.
- В демо-данных историческое задание проводится «сегодня» и затем переносится в прошлое
  (сервисы не дают провести задание задним числом); его отчёт маркировки отправляет воркер.

## Что не сделано и ограничения

- **Дополнительные задачи** (база знаний, поиск поставщиков, голос, экспорт в Excel, E2E и
  CI) — не делались.
- Реестр идущих ответов и счётчик неудачных входов — в памяти процесса: бэкенд — один процесс
  uvicorn.
- Псевдонимы в картинках не заменить: модель просят не подписывать графики именами.
- Распознавание имён — правила, а не NER: двойные фамилии и редкие написания могут не
  распознаться.
- Code Interpreter работает, пока основная и запасная модели у одного провайдера (общие файлы).

Деньги и количества — `numeric` в БД и `Decimal` в коде, по API — строками. Ошибки — текстом
в `{"detail": "..."}`, включая некорректный ввод (огромные номера, символ NUL, переполнение
цены) и ответы самого фреймворка; тест проходит по всем эндпоинтам из OpenAPI.
