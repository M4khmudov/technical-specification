# Technical Specification — свечная мастерская

Мини-система учёта склада и производства для мастерской ароматических свечей
и ИИ-ассистент поверх неё.

## Запуск

```bash
cp .env.example .env   # при необходимости вписать OPENAI_API_KEY
docker compose up -d --build
```

| Сервис | Адрес |
| --- | --- |
| Интерфейс | http://localhost:3000 |
| API и OpenAPI | http://localhost:8000/docs |
| Мок внешних сервисов | http://localhost:8001 |
| PostgreSQL (снаружи) | localhost:5433 |

Миграции применяются автоматически при старте бэкенда.

## Тесты и линтеры

```bash
docker compose exec backend pytest
docker compose exec backend ruff check .
cd frontend && npm run lint
```

Тесты идут на настоящем PostgreSQL в отдельной базе `candles_test`; схема
создаётся теми же миграциями Alembic. LLM в тестах — заглушка, в сеть тесты не ходят.

## Стек и решения

- **Бэкенд:** Python 3.12, FastAPI, SQLAlchemy 2 (async, asyncpg), Pydantic v2, Alembic.
- **Фоновые задачи:** arq + Redis. Выбран вместо Celery, потому что он асинхронный,
  как и весь бэкенд, и не требует отдельного брокера/бэкенда результатов.
- **Фронтенд:** React + TypeScript (Vite), Tailwind. В Docker раздаётся nginx,
  который проксирует `/api` на бэкенд без буферизации (нужно для SSE).
- **Мок-сервисы** (курсы валют, сервис маркировки) — отдельный контейнер `mocks`.
- **Ключи** только из переменных окружения, в репозитории лежит `.env.example`.
- Имя compose-проекта задано явно (`name: candles`), потому что имя папки может быть
  не латиницей.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `users` | сотрудники и их роли |
| `materials`, `suppliers` | справочники |
| `recipes`, `recipe_items` | рецепты: нормы материалов на 1 шт. |
| `receipts`, `batches` | поступления; каждая строка поступления — партия с автономером |
| `batch_movements` | движения по партии (поступление, резерв, снятие резерва, списание) |
| `production_jobs`, `job_materials` | задания и потребность в материалах (норма и факт) |
| `reservations` | резерв конкретной партии под задание |
| `audit_log` | журнал изменений: кто (ФИО снимком), когда, что было, что стало |
| `marking_reports`, `marking_attempts` | отчёты в сервис маркировки и журнал попыток |

- Количества — `numeric(14,3)`, цены и себестоимость за единицу — `numeric(16,6)`,
  курсы — `numeric(12,6)`. В коде только `Decimal`.
- У партии три количества: пришло (`quantity`), физический остаток (`remaining_qty`) и
  зарезервировано (`reserved_qty`). Свободный остаток = остаток − резерв. Инварианты
  (`0 ≤ резерв ≤ остаток`, количества > 0) закреплены CHECK-ограничениями в БД.
- Статусы хранятся строками с CHECK на допустимые значения, а не native enum
  PostgreSQL: добавление статуса не требует `ALTER TYPE`.
- Автономера партий и заданий — отдельные последовательности, не зависящие от `id`.

## Партии и курсы валют

- Каждая строка поступления становится партией со статусом «На проверке» и автономером.
- Себестоимость единицы в рублях = цена × курс на дату поступления, округление до
  6 знаков (`ROUND_HALF_UP`). Курс и дата, на которую он опубликован, сохраняются в партии.
- Мок курсов (`GET /rates/{USD|EUR}?date=`) публикует курс только в рабочие дни,
  как ЦБ: в выходные, праздники и будущие даты — 404. Клиент на бэкенде в этом
  случае идёт назад по дням (до 14 дней — с запасом на новогодние каникулы) и берёт
  последний опубликованный курс. Курсы детерминированы и отдаются строкой.
- Курсы запрашиваются до записи в БД: если сервис курсов недоступен, поступление не
  создаётся частично, а пользователь видит «Сервис курсов валют недоступен…».
- Менять статус можно только у партии «На проверке» (→ «Принята» или «Брак»);
  смена статуса берёт блокировку строки, повторная смена — понятная ошибка 409.
- Ошибки предметной области — исключения с готовым текстом; API отвечает
  `{"detail": "Партия №12 уже в статусе «Принята»…"}` с кодом 400/404/409/503.
- Вход — JWT по логину и паролю (PBKDF2). Проверка прав по ролям — в блоке 5.

## Задания и резервы

- Жизненный цикл: Черновик → Запланировано → В работе → Завершено → Сервис маркировки.
  Отмена — только из «Черновика» и «Запланировано», резервы при этом снимаются.
- Черновик ничего не резервирует. При планировании материалы резервируются по FIFO:
  принятые партии в порядке даты поступления, затем номера. При нехватке —
  частичный резерв и дефицит; кнопка «Дозарезервировать» добирает дефицит из
  новых партий. Запустить задание с дефицитом нельзя: «Нельзя запустить задание №7:
  не хватает 2,5 кг «Воск соевый»».
- **Конкурентность.** Операция блокирует строку задания, затем партии через
  `SELECT … FOR UPDATE` в едином порядке (материал → дата → id). После ожидания
  блокировки PostgreSQL перечитывает строку и заново проверяет «есть свободный
  остаток», поэтому два запроса не возьмут один остаток, а единый порядок исключает
  взаимоблокировки. Тест запускает 6 параллельных резервов по 3 кг на партию в 10 кг
  и проверяет, что отдано ровно 10. Без блокировки тот же тест показывает 18 из 10:
  ORM пишет итоговое значение, и обновления молча затирают друг друга.
- **Завершение** с фактическим расходом считается в два прохода: сначала план
  списания, потом изменения. Резерв списывается по FIFO, экономия возвращается в
  партии, перерасход досписывается из свободного остатка по FIFO. Если перерасход
  не покрыт остатком — ошибка, и ничего не меняется. Материал, для которого факт
  не указан, считается израсходованным по норме.
- «Светофор» компонента: зелёный — всё в резерве, жёлтый — часть, красный — ничего.
- Себестоимость задания: до завершения — оценка по зарезервированным партиям
  (с флагом, если есть дефицит), после — по фактически списанным партиям.

## Допущения

- Дата поступления не может быть в будущем, дата задания — в прошлом.
- Статусы задания: Черновик → Запланировано → В работе → Завершено → Сервис
  маркировки. Отмена возможна только из «Черновика» и «Запланировано».
